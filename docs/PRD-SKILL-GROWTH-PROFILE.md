# PRD：Skill DNA 成长成绩单

> 状态：首版实现中  
> 适用范围：独立的 `skill-growth-scorecard` 展示能力及其上游通用评分契约  
> 不包含：任何真实客户 Skill 的审计结果、联系人、完整本地路径或私有证据

## 1. Summary

把现在偏“审计报告”的结果，升级成一张像 MBTI 能力画像一样好看、好懂、愿意分享的 **Skill DNA 成长成绩单**。

用户打开结果后，30 秒内应该知道三件事：

1. 我的这个 Skill 是什么类型；
2. 当前处于初学、应用、闭环还是专家阶段；
3. 下一关只需要完成什么。

工程事实仍由脚本决定。类型、等级和文案只能解释脚本证据，不能由模型随意打分。

### 1.1 已确定的架构决策

成绩单独立成一个 Skill，但不独立发明分数。四个模块可以分别使用，也可以串联：

1. `agent-work-readiness`：把口头约定整理为工作包，评估 B0–B6；
2. `skill-self-check`：检查 Skill 的结构和使用契约；
3. `skill-ship-safety`：检查文档承诺、实现和外部动作风险；
4. `skill-growth-scorecard`：组合上述 JSON 与可选行为证据，生成一份 JSON 和离线 HTML。

这样既能在用户还没有 Skill 时先训练“把工作说清楚”，又能在 Skill 写出来后
继续评分。原来的检查可视化不删除，而是保留为成绩单中的“检测结果”和“技术证据”。

## 3. Background

### 3.1 当前问题

现有成绩可以准确告诉用户：

- 基础结构是多少分；
- 契约是否清楚；
- 配套材料是否齐全；
- 是否达到静态交付底线。

但它更像检查单。普通用户看完容易记住“我有很多问题”，不容易记住：

- 我擅长什么；
- 我现在处在哪个成长阶段；
- 为什么是这个阶段；
- 修完哪一项最有机会升级。

### 3.2 用户真正要完成的任务

用户不是只想得到一份审计文件。他想确认：

> “我写 Skill 的能力到了什么程度？这个作品有什么风格？下一次怎样比这次更好？”

### 3.3 产品机会

把结果拆成两层：

1. **个人成长层**：基于当前作品证据评价作者已经表现出的类型、能力阶段、优势、成长课题、下一关和徽章；
2. **项目证据层**：原始分数、交付状态、问题 ID、证据位置、限制和验证状态。

个人成长层让人愿意练，项目证据层让人愿意信。项目红灯不得作为个人标签，但也不得从项目证据层消失。

## 4. Objective

### 4.1 产品目标

让没有工程背景的 Skill 作者，也能通过当前作品证据理解自己的 Skill 创作能力阶段，并愿意按下一关继续改进。

### 4.2 用户收益

- 不再面对一堆难懂的技术问题；
- 先看到优势，再看到最重要的成长课题；
- 每次复检都能看到等级、能力轴和徽章的变化；
- 可以分享一张不泄露代码和客户资料的成长卡；
- 技术人员仍能追溯全部原始证据。

### 4.3 成功标准

以下数值是待验证的产品目标，不是当前已有数据：

| Key Result | 目标 |
| --- | --- |
| 快速理解 | 80% 的测试用户在 30 秒内说出“类型、等级、下一关” |
| 行动清晰 | 80% 的测试用户能指出最优先修的一项 |
| 结果可信 | 100% 的等级和类型可以追溯到脚本字段与公开规则 |
| 复检价值 | 完成下一关后，页面能清楚说明哪些能力轴发生变化 |
| 隐私安全 | 分享卡不含完整路径、客户资料、凭证或证据原文 |

### 4.4 非目标

- 不分析作者的人格；
- 不声称这是心理测评；
- 不用模型印象分替代脚本；
- 不把所有能力压成一个 100 分总分；
- 不因为文件长、脚本多就自动判定为高级；
- 不在首版执行目标 Skill 的外部动作。

## 5. Market Segments

分层依据是用户当前要完成的任务，不是年龄或职业。

### 5.1 初学创作者

**行为**

- 第一次或刚开始写 `SKILL.md`；
- 不熟悉契约、验证、脚本和安全术语；
- 更关心“这样算不算写好了”。

**需要**

- 简单结论；
- 鼓励性评价；
- 一次只给一个下一关；
- 用普通话解释技术问题。

**产品重点**

- 类型卡、成长等级、三个优势、一个成长课题；
- 不默认展开代码证据。

### 5.2 应用型作者

**行为**

- 已经写过多个 Skill；
- 开始加入 references、scripts 和工作流；
- 会在真实任务里反复使用。

**需要**

- 知道哪里会漂移、失效或无法复现；
- 看见自己从“能用”到“稳定应用”的差距；
- 比较两次检查结果。

**产品重点**

- 六项能力轴；
- 升级条件；
- 上次与本次变化；
- 可执行的修复任务。

### 5.3 工程型作者与团队

**行为**

- 维护可共享或开源的 Skill；
- 有测试、CI、脚本和平台适配要求；
- 需要团队使用同一套标准。

**需要**

- 稳定、可复现的判断规则；
- 行为证据、安全底线和平台兼容性；
- 机器可读 JSON。

**产品重点**

- 技术证据视图；
- 规则版本；
- 回归测试；
- JSON Schema 和 CI 输出。

### 5.4 负责人和审核者

**行为**

- 不一定亲自写 Skill；
- 主要判断能否交付、风险是什么、修复成本多大。

**需要**

- 一句话结论；
- 当前等级；
- 阻断交付的原因；
- 下一阶段需要投入什么。

**产品重点**

- 业务摘要；
- 交付状态；
- 阶段路线；
- 打印和分享。

### 5.5 首版优先级

1. 优先服务初学创作者；
2. 同时保留工程型用户需要的证据入口；
3. 暂不为企业管理员制作多人排名和团队排行榜。

## 6. Value Proposition

### 6.1 Who

正在编写、改进或审核 AI Skill 的个人和小团队，尤其是不熟悉工程审计语言的作者。

### 6.2 Why

他们需要知道 Skill 是否真正成熟，却不想先读懂一整份技术报告。

### 6.3 What Before

- 得到一组数字和问题列表；
- 不知道这些数字代表哪个成长阶段；
- 不知道自己属于哪种创作风格；
- 不知道先修哪个问题最划算；
- 修完后也缺少成长反馈。

### 6.4 How

- 用确定规则生成一个 Skill 类型；
- 用硬门槛生成成长等级；
- 用六项能力轴解释优势和短板；
- 把当前阶段最值得练习的能力生成“个人能力下一关”；
- 把最高优先级缺陷保留为检测页的“项目优先整改”；
- 保留原始脚本成绩和技术证据；
- 复检时显示“已解锁”和“仍待完成”。

### 6.5 What After

用户可以说：

> “这是一个自动化搭建型 Skill，目前在中级应用阶段。它执行能力强，但验证闭环不足。下一关是补一套可复现测试。”

### 6.6 Alternatives

| 替代方式 | 问题 |
| --- | --- |
| 只看检查清单 | 准确但不容易形成成长感 |
| 只给 100 分 | 简单但会掩盖严重问题，也难解释 |
| 让模型自由点评 | 有趣但不稳定，同一输入可能得到不同结论 |
| 人工专家评审 | 深入但慢，难以每次复检 |

### 6.7 一句话价值主张

**Skill DNA 成长成绩单把枯燥的工程检查变成一张可解释、可进化、可分享的创作画像，同时保留每一个结论背后的技术证据。**

## 7. Solution

### 7.1 产品模型：类型和等级必须分开

类型回答：

> “我在当前作品中表现出哪一种 Skill 创作风格？”

等级回答：

> “当前证据说明我的 Skill 创作能力到了哪一步？”

同一个类型可以出现在不同等级。  
例如“自动化工匠”既可能是刚会写脚本的初学者，也可能是有完整测试和安全闸门的高级作者。

页面必须写清楚：

> 这是基于当前作品证据的个人能力画像，不是人格定型；项目能否交付在检测结果中单独判断。

### 7.2 六项能力轴

每个能力轴使用 0—4 级证据状态，不直接拼成 100 分。

| 能力轴 | 用户能听懂的解释 | 主要证据 |
| --- | --- | --- |
| 目标与边界 | 知不知道什么时候该用、什么时候不能用 | When / When NOT / check axes / SMART |
| 流程与执行 | 能不能把任务一步步做完 | actionable steps / scripts / command implementation |
| 工具与材料 | 有没有说明、样例、脚本和状态材料 | references / examples / memory / scripts |
| 验证与复盘 | 做完后能不能证明、失败后能不能改 | verification / tests / PDCA / retry |
| 安全与控制 | 会不会在未确认时发消息、改数据或访问外部系统 | dry-run / confirmation / ship safety / write-back |
| 通用与适配 | 换模型、平台、目录或系统后还能不能工作 | CLI/JSON contract / adapters / portable paths / platform evidence |

证据状态统一为：

| 状态 | 含义 |
| --- | --- |
| 0 未说明 | 文档没有明确承诺 |
| 1 已说明 | 文档提出了规则或目标 |
| 2 已实现 | 当前文件中有对应实现 |
| 3 已测试 | 有脱敏夹具或自动测试证明 |
| 4 已验证 | 在可信环境或多个平台有可复核行为证据 |
| ? 待确认 | 当前扫描能力无法安全判断，不能当作 0 分 |

### 7.3 成长等级

等级使用硬门槛。严重问题不能被其他高分平均掉。Lv0 也只适用于已经能确认是
一个 Skill 包的早期草稿；项目工作区、素材库或混入运行产物的目录不进入等级表。

| 等级 | 用户称号 | 能力描述 | 最低条件 |
| --- | --- | --- | --- |
| Lv0 | 灵感草稿 | 有想法，但还没有形成可调用 Skill | 文件或元信息不能稳定识别 |
| Lv1 | 初学者 · 起步创作者 | 已经能被识别，也有基本步骤 | 基础结构达到最低要求 |
| Lv2 | 入门应用 · 实用搭建者 | 规则较清楚，配套材料基本齐全 | 静态交付底线通过；无脚本严重问题 |
| Lv3 | 中级应用 · 稳定实践者 | 核心流程能跑，并有可复现验证 | Lv2 + 核心路径测试 + PDCA 闭环证据 |
| Lv4 | 高级应用 · 闭环工程师 | 外部动作受控，失败可恢复，适合正式交付 | Lv3 + 安全扫描通过 + 写回一致性 + 失败恢复 |
| Lv5 | 专家级 · 跨平台架构师 | 能在不同 Agent 平台复用，有统一能力契约 | Lv4 + 至少两个平台的兼容证据 + 平台适配层 |

#### 等级保护规则

1. `package_health.assessable=false` 时不显示 Lv0–Lv5、类型或徽章，根结论为
   `invalid_skill_package`；原始分数只作局部文件诊断；
2. `stop_ship` 时最高只能显示 Lv1 或 Lv2，具体上限由阻断类型决定；
3. 没有行为证据时不能进入 Lv3；
4. 没有安全和失败恢复证据时不能进入 Lv4；
5. 只写“支持多个平台”不能进入 Lv5，必须提供复核证据；
6. 未知状态显示“待确认”，不能偷偷当成通过；
7. 所有门槛写入版本化脚本并有回归测试。

### 7.4 Skill 类型

首版使用 6 个主类型和 1 个稀有平衡类型。名称保持正向，但不能掩盖成长课题。

| 类型 | 典型优势 | 常见成长课题 | 主要能力组合 |
| --- | --- | --- | --- |
| 🧭 流程探路者 | 目标大、场景广、善于规划整条链路 | 容易先铺范围，后补验证 | 目标与边界 + 流程与执行 |
| 🧱 稳健搭建者 | 结构清楚、说明完整、容易上手 | 需要继续增加真实行为证据 | 目标与边界 + 工具与材料 |
| ⚙️ 自动化工匠 | 脚本多、执行力强、重视效率 | 容易低估默认关闭和失败恢复 | 流程与执行 + 工具与材料 |
| 🔁 闭环教练 | 重视检查、复盘、重试和持续改进 | 可能实现速度较慢 | 验证与复盘 + 目标与边界 |
| 🛡️ 安全守门员 | 权限、确认、审计和回写控制强 | 需要避免规则过重影响使用 | 安全与控制 + 验证与复盘 |
| 🌐 跨平台架构师 | 契约稳定、适配清楚、迁移成本低 | 需要控制抽象复杂度 | 通用与适配 + 目标与边界 |
| ✨ 六边形选手 | 六项能力稳定，没有明显短板 | 继续积累真实规模与长期证据 | 六轴均达到 3，且最高最低差不超过 1 |

#### 类型生成规则

1. 脚本先计算六项能力轴；
2. 每个类型有公开、版本化的能力组合规则；
3. 选择得分最高的主类型；
4. 分数相同时使用固定顺序，不交给模型临时决定；
5. 可以显示一个副标签，例如“偏自动化”或“重验证”；
6. 模型只负责把结构化结果写成自然语言评价；
7. 证据不足时显示“类型待解锁”，不强行贴标签。

首版不做 16 个复杂类型。先验证用户是否喜欢“类型 + 等级 + 下一关”，再决定是否增加更多组合。

### 7.5 成绩单首屏

首屏只回答五件事：

1. **你的 Skill 创作类型**：例如“自动化工匠”；
2. **当前能力阶段**：例如“Lv3 中级应用 · 稳定实践者”；
3. **一句评价**：先讲优势，再讲最关键的成长课题；
4. **三项天赋**：来自已经通过的证据；
5. **下一关**：只给一个最优先任务。

推荐文案结构：

> 【具体能力判断，例如：你擅长把复杂任务做成可执行工具】  
> 从这份 Skill 的【证据来源】看，你已经具备【已表现出的能力】。  
> 目前处于【能力阶段】。  
> 当前最值得补强的是【最多三项证据短板】。

这段话必须像一份个人能力评价，不能写成产品说明或界面说明。以下
“元文案”不得出现在正式成绩单中：

- “类型讲创作风格，等级讲能力阶段”；
- “这张成绩单用于评价……”；
- “随着证据增加，画像会继续变化……”。

这些内容可以放在帮助文档里，但不能占用个人能力卡。个人能力卡必须
直接回答“你已经表现出什么能力、目前到了哪一步、下一步练什么”。
`stop_ship`、`暂停交付` 等项目状态仍只在检测结果和技术证据中展示。

### 7.7 核心功能

#### A. 类型揭晓

- 类型名称；
- 一句类型介绍；
- 三个优势；
- 一个成长课题；
- “为什么是这个类型”证据入口。

#### B. 等级与升级

- 当前等级；
- 已通过门槛；
- 未通过门槛；
- 下一等级只差什么；
- 严重问题对等级的封顶说明。

#### C. 六项能力轴

- 不使用夸张雷达面积制造“总分感”；
- 优先使用六条独立进度轨；
- 未验证项显示问号；
- 点击能力轴可查看证据和提升方法。

#### D. 下一关

“个人能力下一关”和“项目优先整改”必须分开：

1. **个人能力下一关**服务于作者成长，说明应该学习和练习什么；
2. **项目优先整改**服务于当前作品，说明必须修复哪个问题；
3. 个人练习不得出现 `CMD.2`、`stop_ship` 等项目问题编号或交付状态；
4. 项目整改不得因为成长文案变得更友好而被删除、降级或隐藏；
5. 每个能力等级都必须有独立练习模板，并写明练习内容和练成标准。

Lv1 自动化类型的个人练习应包含：

- 学习把目标写成输入、输出、成功阈值、停止条件和升级条件；
- 学习分别处理正常、资料不足、无权限和执行失败；
- 学习把重复逻辑整理为可传参、可返回状态的复用脚本；
- 理解 Harness 位于目标 Skill 外部，负责用脱敏输入驱动、记录和检查，
  不负责真实业务发送。

#### E. 徽章

徽章只奖励证据，不奖励文件长度。

首版可用徽章：

- `说明书已成型`
- `边界说清楚`
- `样例可复现`
- `自动测试通过`
- `安全默认关闭`
- `失败可以恢复`
- `双平台验证`
- `闭环完成`

#### F. 两种视图

- 成长视图：给普通用户；
- 工程证据：给开发者和审核者。

两种视图必须读取同一份 JSON。结论、数量和 ID 不能不同。

#### G. 复检变化

- 上次等级和本次等级；
- 能力轴变化；
- 新解锁徽章；
- 已解决的问题；
- 新出现的问题；
- 不使用“连续签到”逼迫用户刷分。

#### H. 分享卡

分享卡只包含：

- Skill 显示名；
- 类型；
- 等级；
- 三项优势；
- 一个下一关；
- 规则版本和生成日期。

分享卡不得包含：

- 完整本地路径；
- 客户名称和联系人；
- 代码片段；
- 私有证据；
- 凭证和外部账号信息。

### 7.9 技术方案

建议增加：

```text
scripts/
  hard_gates.py
  ship_safety.py
  profile_engine.py       # 只做确定性派生

schemas/
  audit-result.schema.json
  skill-profile.schema.json

templates/
  scorecard.html          # 离线展示模板

tests/
  test_profile_engine.py
  fixtures/profile/
```

`profile_engine.py` 的责任：

1. 读取 hard gates 和 ship safety 的 JSON；
2. 读取可选的行为证据清单；
3. 计算六项能力轴；
4. 按公开门槛决定等级；
5. 按固定规则决定类型；
6. 根据类型、等级、能力轴和问题 ID 生成 `personal_interpretation`；
7. 生成与项目问题编号解耦的 `learning_quest`；
8. 选择项目整改项和徽章；
9. 输出单一 JSON；
10. 不调用模型，不执行目标 Skill。

模型的责任：

- 在产品设计阶段帮助维护普通话文案模板；
- 通过人工评审发现生硬、空泛或带有误导性的表达；
- 不修改等级、类型、数量、ID 和结论。

运行时不依赖模型临时发挥。正式成绩单中的能力评价由版本化模板和
结构化证据确定性生成，HTML 只展示 `personal_interpretation`。

### 7.10 内容语气

#### 应该

- 评价个人在当前作品中已经表现出的能力，不做人格定型；
- 使用具体、可感知的能力判断，例如“把业务任务拆成步骤、脚本和执行路径”；
- 先说做对了什么；
- 再说当前阶段和最多三项成长重点；
- 使用“成长课题”“下一关”“待解锁”；
- 清楚说明为什么没有升级。

#### 不应该

- “你能力不行”
- “这个 Skill 很差”
- “综合得分 78，所以可以交付”
- “大概是高级水平”
- “看起来支持所有平台”
- “类型讲创作风格，等级讲能力阶段”
- “这张成绩单用于评价你的能力”
- 用有趣文案掩盖 `stop_ship`
- 在个人能力卡上使用“暂停交付”等项目状态标签

### 7.11 关键验收条件

- [ ] 同一份输入在同一规则版本下得到相同类型和等级；
- [ ] 修改解释文案不会改变任何分数、类型或等级；
- [ ] 个人能力卡直接给出能力判断、阶段判断和成长重点，不出现解释页面设计的元文案；
- [ ] `personal_interpretation` 由 Python 根据同一份证据确定性生成，HTML 不临时拼装评价；
- [ ] 成长页显示 `learning_quest`，检测页显示项目整改；两者不共用一段文案；
- [ ] 个人能力下一关不出现问题编号、交付阻断或“修复当前项目”的措辞；
- [ ] Lv0–Lv5 每一级都有量化目标、判断流程、复用或验证等可练习动作；
- [ ] `stop_ship` 不会显示“可以正式交付”；
- [ ] 个人成长卡不显示 `stop_ship` / “暂停交付”等项目状态徽章；
- [ ] 检测结果和技术证据仍完整显示项目交付结论；
- [ ] 没有行为证据时不能进入中级应用以上的行为等级；
- [ ] 每个类型、等级、徽章和下一关都有证据 ID；
- [ ] 未知项显示“待确认”，不显示为通过；
- [ ] 成长视图和工程视图的数据完全一致；
- [ ] 普通用户 30 秒内能找到类型、等级和下一关；
- [ ] 页面支持桌面、移动、键盘和打印；
- [ ] HTML 无外部字体、CDN 和追踪；
- [ ] 页眉、检测结果、技术证据和 JSON 都能确认当前分析对象；
- [ ] 分享卡不包含路径、客户资料、凭证和私有证据；
- [ ] 真实审计结果默认写入仓库外的私有交付目录；
- [ ] 类型和等级规则有单元测试和固定夹具；
- [ ] 当前规则版本显示在结果页。

### 7.12 主要假设

这些假设需要通过用户测试确认：

1. 类型名称比单纯数字更容易被记住；
2. “等级 + 下一关”会提升复检意愿；
3. 6 个主类型已经足够，不需要首版做 16 类型；
4. 用户能理解“个人能力画像基于作品证据”与“固定人格判断”不同；
5. 初学者愿意在需要时展开技术证据；
6. 不使用总分不会降低用户对成绩单的兴趣；
7. 公开门槛不会导致用户只为刷等级而堆文件。

### 7.13 风险与防护

| 风险 | 防护 |
| --- | --- |
| 类型像随意贴标签 | 类型由脚本计算，并显示证据 |
| 有趣文案淡化严重问题 | 个人卡不贴项目红灯；检测结果和技术证据始终保留完整交付结论 |
| 用户为了升级堆文件 | 只奖励行为证据和可复现结果 |
| 初学者被“Lv1”打击 | 先讲已表现出的优势，等级描述当前可证明的能力阶段而不是永久能力上限 |
| 高级用户觉得太卡通 | 提供一键切换工程证据视图 |
| 结果包含客户隐私 | 默认脱敏；分享卡使用白名单字段 |
| 不同平台结果漂移 | 核心计算放在 stdlib 脚本，不交给模型 |

## 8. Release

### 8.1 第一版：可用原型

包含：

- 6 个主类型 + 1 个平衡类型；
- 6 个成长等级；
- 六项能力轴；
- 类型卡、等级、优势、成长课题和下一关；
- 成长视图与工程证据视图；
- 单文件离线 HTML；
- 手工准备的脱敏 JSON 夹具。

不包含：

- 多人排行榜；
- 云端账户；
- 自动分享；
- 真实外部行为执行；
- 16 类型组合。

### 8.2 第二版：自动生成

- 实现 `profile_engine.py`；
- 定义 JSON Schema；
- 接入 `hard_gates.py` 和 `ship_safety.py`；
- 增加类型、等级、封顶规则和隐私测试；
- 支持前后两次结果对比。

### 8.3 第三版：行为与平台证据

- 接入可信隔离测试结果；
- 支持平台能力清单；
- 记录至少两个 Agent 平台的兼容证据；
- 解锁 Lv3—Lv5 的完整判定；
- 评估是否扩展为更多类型组合。

### 8.4 上线前验证

1. 用项目现有正常夹具和坏夹具生成画像；

3. 邀请初学、应用、工程三类用户试读；
4. 让用户在 30 秒内回答类型、等级和下一关；
5. 检查成长视图和技术视图的数字、ID、结论完全一致；
6. 扫描 HTML、JSON 和分享卡，确认没有客户资料与完整本地路径；
7. 在桌面、移动、打印环境完成浏览器验证。
