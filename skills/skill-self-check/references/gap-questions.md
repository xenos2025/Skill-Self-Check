# Gap questions — 把「只有用户知道的空缺」问出来

Use this after the report is drafted (Pass 3 / Pass 5). Some gaps are business
decisions, not writing problems. Ask for them instead of inventing them.

## 分流：能推断的直接改，属于决策的先问

| 类型 | 典型 finding | 做法 |
| --- | --- | --- |
| 措辞、结构、行数、术语、把长内容挪走 | 大部分 `2.x` / `4.x` | 直接给可粘贴改法，不要占用用户 |
| 业务边界、触发场景、验收凭据、出错找谁 | `1.7` `3.2` `3.3` `3.5` `5.3` `5.4` | 先问，拿到答案再写 |

模型编一个"通用说法"填进去，比留空更糟：分数会变好看，skill 跑起来照样不对。

## 三条硬规则

1. 只问同时满足两个条件的 finding：severity 是 `critical` 或 `should_fix`；且答案只有用户知道。
2. **一次一个问题，等回答。** 一轮最多 3 个；剩下的写进报告的「还需你确认」清单，不要连珠炮。
3. 用户答「不知道 / 你看着办」时，给候选答案让他挑；仍不确定就记 `unknown — 待用户确认`，不要写进 `SKILL.md` 当事实。

能从文件、脚本输出、已连接工具里查到的，自己查，不要问用户。

## 映射表

| Finding | 问这一句 | 为什么不能替用户答 | 答案写回 |
| --- | --- | --- | --- |
| `1.7` description 没有 WHEN 触发 | 「你说哪句话的时候，AI 就该自动用上它？给我一两句你平时的原话。」 | 触发词是这个团队的口头说法（"看下这个客户靠不靠谱"），模型写的通用词命不中 | frontmatter `description` 后半句 |
| `3.2` 何时使用 缺正向触发 | 「上周有没有真发生过一次该用它的情况？说说当时是什么场景。」 | 真实场景决定了步骤顺序，编的场景会推导出错的流程 | `## 何时使用` |
| `3.3` 缺 何时不用 | 「什么情况下**不该**用它？有没有必须人来拍板、AI 不能碰的事？」 | 哪些决定不能交给 AI（报价、放行、拒单、承诺交期）只有业务方清楚 | `## 何时不用` |
| `3.5` / `5.3` 验收没有证据 | 「做完之后，你看什么就知道它做对了？一张截图、一个表格字段，还是某个数字？」 | 凭据取决于这家公司实际在用的系统和单据 | `## 验收` |
| `5.4` 缺 Act（出错没出口） | 「它要是做错了或者卡住了，下一步找谁？怎么退回去重来？」 | 升级路径是这家公司的岗位安排 | `## 常见借口` / `## 危险信号` / 重试路径 |
| `6.3` 落地记忆无字段 | 「跨次要记住什么？存在哪个文件？必填字段有哪些（比如 sent_at）？常规要不要截图？」 | 记什么、存哪、要不要截图是运营策略 | 发送记录结构 / `## 配套模块` |

## 怎么问（面向 AI 初学者）

- **先给候选再问。** 让人改比让人想容易：「我建议写成 X，因为 Y；如果其实是 Z，你纠正我。」
- **口号答案追问一次。** 「'做好客户维护' 我没法写进验收——是发一封跟进邮件，还是更新 CRM 里某个字段？」
- **不要在一句话里塞两个问题。** 「谁做、什么时候做」拆成两轮。
- **不要用行业常识补空。** 同一条纪律在 `exp/pm-workflow-planning/INTERVIEW.md` 里也适用。

## 可粘贴模板

拿到答案后，用用户的原话填进对应模板，放进报告等确认。

```markdown
## 何时使用

- <用户描述的真实场景 1>
- 用户说「<原话触发词>」时
```

```markdown
## 何时不用

- <必须由人拍板的事>——交给 <角色>
- <明确排除的相邻场景>
```

```markdown
## 验收

- [ ] <可观察的凭据：截图 / 表格字段 / 数字 / 脚本输出>
- [ ] <出现异常时记录了什么>
```

```markdown
## 危险信号

- <用户描述的"这就说明做错了"的现象>
- 卡住或拿不准时：停下，交给 <角色>
```

## 落盘闸门

问答产出的是**待确认文本**，先只放进报告。用户说「按意见改」或「就这么写」之后，才写进目标 `SKILL.md`。这和直接改文件共用同一道闸，不另开口子。
